# Project Map

A file-by-file guide to what each part of this codebase does. Companion reference to [README.md](README.md) — use this to navigate straight to the code behind any specific claim in it.

---

## Backtesting Methodology (Phase 1) — `candidates/`

- **`methodology.py`** — Core statistical engine, shared by every candidate (static and dynamic, production and replay). `build_events()` (causality-safe entry, always the bar after a trigger), `pattern_significance()` (**the actual acceptance gate**: walk-forward per-fold horizon selection, then a 2,000-resample bootstrap test of the held-out forward return against that coin's own unconditional baseline over the same calendar stretch, plus the MFE/MAE risk-path ratio), `classify_status()` (turns a report + concentration check + pattern result into `accepted`/`watch`/`rejected`/`insufficient_data`, in that exact branching order — concentration is checked *before* significance, a real bug once inverted, see `docs/case_study/methodology-decisions.md`), `explain_non_acceptance()` (the SPECIFIC reason a candidate isn't `accepted`, mirroring `classify_status`'s own branching — never a generic or misleading line), `STATUS_PLAIN` (plain-English gloss for each status code), `format_trigger_summary()` (powers `/summary`/`/replay_summary` — groups every tracked candidate by status, capped/compacted so the message never grows unbounded), `format_candidate_details()` (powers `/details`/`/replay_details` — the full numeric breakdown for one named candidate: N, p-value, excess return, MFE/MAE ratio, coin/year concentration percentages, reference TP/SL stats, `explain_non_acceptance()`'s reason if applicable, and — a real gap fixed after being caught live: whether the candidate is `VALIDATED`, from its `all_latest_statuses()` entry — `status` (accepted/watch/rejected) and `validated` are different claims, see "accepted vs validated" below, and the two were never shown together in this one command until this fix, even though a candidate can be both `accepted` and already `VALIDATED` at once; takes the trigger's own definition string, current holding horizon, and milestone info as parameters rather than looking them up, so this module gains no dependency on `candidates/definitions.py`, the dynamic-condition registry, or either production's/replay's own live-test-state or status-history module), `path_outcome()` (the live-test resolution primitive: forward return + MFE + MAE for one real occurrence, the same convention `pattern_significance` uses), `compute_anchors()`/`walk_forward()`/`report()` (duration-bucketed TP/SL levels and the informational win-rate/Sortino reference stats — no longer gate acceptance, still computed and shown), `concentration_check()`, `shock_zscore_series()`/`classify_regime()`.
- **`definitions.py`** — The three trigger families under test (C1 funding-rate crowding, C2 post-macro-release reaction, C6 efficiency-ratio trend — C3/C4/C5 were part of the prior research's larger set but weren't carried forward), each a pure function of price/volume/funding data. `compute_triggers(df, funding, scale=1)` — `scale=24` reinterprets every day-defined rolling window as its hour-equivalent for the hourly mechanical live-trigger scan (never the backtest, which always uses `scale=1`); `shock_zscore`/`is_macro_day` are the deliberate exceptions that stay calendar/daily-native regardless of `scale`. `TRIGGER_DESCRIPTIONS` (prose, one per base candidate — grounds an LLM call in what a trigger actually tests) and `TRIGGER_NUMERIC_DEFINITIONS` (the same, but with the exact numeric threshold instead of prose, e.g. "funding z-score below -2.0" rather than "an extreme funding rate" — must be kept in sync with `compute_triggers()` by hand, since it's a duplicated description, not a derived one) power `telegram/bot.py::_trigger_description()`/`_trigger_numeric_description()` respectively.
- **`data_loading.py`** — Loads historical OHLCV and funding-rate series from `data/`.
- **`macro_calendar.py`** — FOMC/CPI release calendar, at calendar-day granularity.
- **`macro_vintage.py`** — Point-in-time-correct macro release lookups (`vintage_releases_as_of`, `latest_release_with_prior`, `recent_releases_summary`) — a macro figure is only "known" to Sonnet as of its real publication date, never a later-revised value. Shared by production and the replay (`replay/time_sandbox.py` re-exports this module rather than duplicating it).
- **`run_battery.py`** — Orchestrator: runs every static and dynamic candidate through `methodology.py`, assigns a live status (`accepted` / `watch` / `rejected` / `insufficient_data` / `error`), and writes `execution/live_battery_state.json` (`SIGNAL_STORE_PATH`) — the file everything else reads "what's currently accepted" from. Also re-derives and re-syncs every candidate's horizon (`execution/live_test_state.py::save_horizons()`) every run a pattern-significance result exists for it, independent of accepted/watch/rejected — mirrors `replay/battery.py`'s own sync exactly (a real gap, fixed: this used to only ever be set once, at the moment a human approved a novel condition, never refreshed by the weekly run afterward). Each candidate is isolated in its own try/except (see "Partial Failures & Crashes" below).
- **`status_history.py`** — Tracks every candidate's status history. Two independent mechanisms: `candidates_due_for_prune_decision()` (2+ calendar years tracked, never once `accepted` — the safety net for a trigger too rare to ever reach its first live-test milestone) and `candidates_due_for_milestone()`/`mark_milestone_reported()` (fires at every new multiple of 50 in whatever count its caller passes in, not once — this is the ONLY place this project calls a candidate `validated`: `accepted` **and** it has survived 50 occurrences of the kind that count for its own origin, re-earned fresh at each checkpoint, never a permanent badge; stays fully origin-agnostic itself — see `_effective_milestone_count()` in `execution/live_testing.py`/`replay/engine.py` for what actually gets counted and why it differs by static vs. dynamic). `record_horizon()` tracks the empirically-derived holding horizon per candidate, notifying on its first real value or any later change.

## Historical & Market Data — `data/`

- OHLCV data (daily/hourly) for 7 coins (BTC, ETH, BNB, XRP, DOGE, ADA, LTC) from Binance spot, funding-rate history, and macro series (CPI, Fed funds rate, initial jobless claims) from FRED. Coverage: from each coin's real listing date through the present — kept current by `data_ingestion/market_data/binance_fetcher.py` below, not a frozen snapshot. Exactly these 7 coins everywhere in the repo (a prior attempt at SOL/AVAX/LINK was tried and excluded — see `run_battery.py`'s own docstring — and their leftover data files were removed rather than left stale and unfetched).

## Live Data Refresh — `data_ingestion/market_data/`

- **`binance_fetcher.py`** — `update_ohlcv()`/`update_funding()` pull new candles/funding entries from Binance's public API (no key needed) and append them to `data/`. **Genuinely paginates from a real anchor (`BACKFILL_SINCE = "2017-01-01"`) rather than one bounded call** — a real, fixed bug: Binance's `since=None` returns the *most recent* candles, not the earliest (verified live), so a from-scratch backfill (a new coin, or this repo cloned somewhere `data/` isn't already populated) was silently truncating to ~2.7 years of the newest history instead of full depth, with no error. Now loops until a page comes back short of `limit` (genuinely caught up to "now") or `MAX_FETCH_PAGES` is hit (safety net). `update_all()` isolates each coin's fetch so one failure doesn't block the other six.

## News Ingestion — `data_ingestion/news_sentiment/`

- **`cryptocompare_fetcher.py`** — Fetches headlines from the CryptoCompare News API. The only file in this folder used by the live pipeline.

## LLM Judgment Layer (Phase 2) — `llm_pipeline/`

- **`haiku_sonnet_pipeline.py`** — The adaptive layer, narrowed to exactly two live roles. `haiku_scout()` (Claude Haiku screens every headline for asset/sentiment/magnitude/event type). `sonnet_strategist()` (Claude Sonnet, only for escalated headlines — real indicator snapshot, last-10-day macro releases, real battery status; returns `no_action` or `propose_novel_test`, nothing else). `sonnet_shock_response()` (same judgment for a detected volatility shock, `SHOCK_SYSTEM_PROMPT`). `sonnet_prune_advice()` (a lightweight, explicitly-unverified opinion feeding the keep/drop and milestone decisions). `format_spec_clauses()`/`format_sonnet_message()`/`format_shock_message()` render a proposed condition in plain English (`INDICATOR_PLAIN_NAMES`/`OPERATOR_PLAIN` from `novel_condition_tester.py` — never a raw variable name or a bare `<`/`>` symbol, which was once observed to render as a literal `&gt;` on Telegram). `PROPOSAL_KEYBOARD_TEMPLATE` attaches Test It / Don't Test It buttons to every proposal — replaced an earlier free-text "reply 'test it'" convention that silently did nothing for any phrasing that didn't match one of a few exact strings. `run_once()` (headline pipeline) and `run_shock_scan()` (shock pipeline) each isolate every individual item in its own try/except — one malformed model response can't silently stop the rest of that run.
- **`novel_condition_tester.py`** — `SUPPORTED_INDICATORS` (12 whitelisted indicators — RSI, ATR%, Bollinger %B, Donchian position, funding/volume z-scores, trend efficiency, `shock_zscore`, etc. — a fixed indicator+operator+threshold grammar, never arbitrary generated code), `INDICATOR_PLAIN_NAMES`/`OPERATOR_PLAIN` (plain-English translation for every indicator and comparison shown to a human), `test_novel_condition()` (runs a proposed condition through the exact same `methodology.py` pipeline as the static battery, including the same shock-regime exclusion unless the condition being tested IS the shock indicator itself), `condition_desc()`/`format_pattern_significance()` (shared rendering used by every message that shows a tested condition).
- **`shock_detector.py`** — Real-time detection of extreme volatility, reusing the same statistical definition of "shock" as Phase 1.
- **`context_builder.py`** — `build_context_summary()` (currently-accepted candidate names + the "already tested via 'test it' and not accepted" name list — deliberately never capped, since Sonnet needs it to avoid re-proposing a duplicate). `build_live_test_summary(top_n=15)` (by-candidate and by-candidate-and-coin live-test performance, capped at the top 15 rows by `|mean_return|` with a pointer to `/summary` for the rest — fixed after a real measured incident where this context grew to ~10,400 tokens at 96 tracked candidates; see "Cost Optimization" below). `build_technical_snapshot()` queries a Freqtrade SQLite trade database for "open positions"/"last closed trade" — a holdover from the superseded execution model (see "Trade Execution" below); since no funded position is ever placed under the current model, this table never receives a real entry.
- **`dynamic_candidates.py`** — Persistent registry of conditions discovered live (`record_test_result()`, called regardless of verdict — accepted, watch, or rejected — so a rejected condition isn't silently re-proposed and an accepted one isn't trusted forever from one test), re-tested weekly alongside the static candidates by `run_battery.py`.
- **`pending_tests.py`** — FIFO queue of novel-condition proposals, each with its own short `id` embedded in that proposal message's own Test It / Don't Test It buttons (`push_pending_test()` returns the id; `pop_pending_test_by_id()`/`discard_pending_test_by_id()` resolve or dismiss the *exact* proposal a button was pressed on — never "whichever one happens to be oldest," which is what the earlier free-text design did). Entries expire after 48h so an unanswered proposal doesn't sit forever.

## Historical Replay — `replay/`

A day-by-day walker through real 2017-present history, entirely isolated from production's own state (`replay/state/`, gitignored, never shared with `candidates/status_history.json` or any file under `execution/`). Same statistical methodology and live-test model as production, run against real historical data compressed into a short, continuous burst — used to validate the methodology and build an initial live-test track record before actually going live, and this project's own primary demonstration mechanism. Real run so far: reached 2023-06-04 from a 2017-08-26 start (stopped only by Anthropic credit exhaustion, not a bug — checkpoint resumes cleanly), 96 tracked candidates (6 static + 90 discovered live via Sonnet proposals), 1,728 live tests opened, 1,714 resolved.

- **`battery.py`** — `run_replay_battery(as_of)`: mirrors `candidates/run_battery.py` exactly, sourced entirely from as-of data (`time_sandbox.py`) instead of full history, so a status computed on a given simulated day can never see data from after it.
- **`judgment.py`** — `judge_event()` (Sonnet's judgment for one real, dated macro release or shock — the same narrow, bounded context production's `sonnet_strategist`/`sonnet_shock_response` use), `answer_market_question()` (free-text Q&A, `_trades_by_candidate_summary()`/`_trades_by_candidate_and_coin_summary()` capped at top 15 by `|mean_return|`, `_all_candidates_status_summary()` compacting the `insufficient_data` bucket to a count-plus-name-list — the same fix as production's `context_builder.py`, for the same reason), `format_telegram_message()` (mirrors production's proposal message format exactly, no "this is a simulation" framing inside the message body).
- **`engine.py`** — `advance(chunk_days)`: the actual day-by-day walker, halts (`checkpoint.status = "waiting_for_human"`) whenever a novel-condition test is proposed until `resolve_pending_test()` (Test It) or `discard_pending_test()` (Don't Test It) is called, via `REPLAY_PROPOSAL_KEYBOARD`. `_open_live_test()`/`_check_live_tests()` (no TP/SL, holds for `pattern_significance`'s own horizon, resolves via `path_outcome`), `_scan_mechanical_triggers()` (unattended, hourly-resolution detection — `_static_triggers_full` precomputed once per chunk on the *full* hourly series, not a sliced window, after a real bug where slicing first starved rolling-window indicators of their lookback and silently produced all-NaN/False), `_check_prune_decisions()`/`_check_n50_milestones()` (the same two keep/drop mechanisms as `candidates/status_history.py`, driven by the replay's own simulated clock instead of real wall-clock time), `_check_consecutive_failures()` (mirrors `execution/live_testing.py`'s own version exactly — a fast, informational-only losing-streak alert for VALIDATED candidates only), `_send_checkpoint_digest()` (a status summary every ~30 simulated days).
- **`state.py`** — Replay's own isolated state store: `checkpoint.json` (simulated date + run status), `battery_status.json`, `trade_log.json`, `dynamic_candidates.json`, `pending_test.json`, `horizons.json`, and a deferred-reveal queue (`queue_reveal()`/`due_reveals()` — a "test it" result surfaces on its own scheduled day, not instantly, so a rapid string of simulated messages still reads as a coherent history spread over real calendar time).
- **`status_history.py`** — Same two mechanisms as `candidates/status_history.py` (2-year prune safety net, N=50 recurring milestone), keyed off the simulated `as_of` date instead of `datetime.now()`.
- **`time_sandbox.py`** — `daily_as_of()`/`funding_as_of()`: slices real market data to "as of this simulated date," the mechanism that makes the whole replay causality-safe. Re-exports `candidates/macro_vintage.py` rather than duplicating it.
- **`orchestrator.py`** — `run_to_completion()`: a batch driver that repeatedly calls `advance()`.

## Cost Optimization — what actually gets sent to Anthropic

Pricing (verified against [platform.claude.com/docs/en/about-claude/pricing](https://platform.claude.com/docs/en/about-claude/pricing), not assumed): **Claude Sonnet 5** $2 / $10 per million tokens (input / output), **Claude Haiku 4.5** $1 / $5. Every number below is measured against this project's own real calls and real accumulated state, not a generic estimate.

This section is in three parts, deliberately separated because they answer different questions about money: **Part 1** is the one-time cost of building and stress-testing this case study against nine years of real history (the historical replay) — not something that recurs once the demo exists. **Part 2** is the ongoing, recurring cost of actually running the system live (Anthropic API only). **Part 3** is server/hosting cost, kept separate from both because it's a non-Anthropic line item.

---

### 🧪 Part 1 — Building & Stress-Testing This Case Study (Backtest / Replay), a One-Time Cost

The historical replay (`replay/`) is this project's own demonstration mechanism — walking a simulated clock through real 2017-2026 history in a short, continuous burst to show how the system would actually have behaved, generating this case study's evidence. It is not part of normal live operation and isn't meant to be re-run routinely; this is the cost of *producing* the case study, paid once (barring a future methodology change big enough to warrant re-validating against history again).

This project's LLM calls split into two kinds with deliberately different context budgets, because they answer two different questions — this split is the actual mechanism behind every number in this section, both here and in Part 2:

**1. Automated per-event judgment** — `judge_event()` (`replay/judgment.py`), `sonnet_strategist()` / `sonnet_shock_response()` (`haiku_sonnet_pipeline.py`). Fires on every real macro release, volatility shock, or escalated headline — hundreds of times over any long observation window, so this is the actual cost driver. Its context answers one narrow question ("is *this* event worth escalating") and is built to stay **flat regardless of how much history has accumulated**:
  - the one event description (a headline, a macro release, a shock reading)
  - current indicator readings for the relevant coin(s) only — not a history of past readings
  - macro releases from the last 10 days only — not the full calendar
  - the currently-*accepted* candidate names, one line — not every candidate ever tracked
  - a two-line aggregate stat, not a per-trade history

  Measured real call (a macro event, all 7 coins' indicators): **~1,230 tokens** input, ~$0.01/call at current pricing. This number does not grow as the candidate registry or the live-test log grows — none of its five inputs are keyed to either.

**2. Human-triggered Q&A** — `answer_market_question()` (`replay/judgment.py`), `handle_natural_language()` (`telegram/bot.py`). Fires only when a human asks something free-form on Telegram. This one legitimately needs more breadth, since it has to be ready for *any* question ("what's accepted", "how's candidate X doing", "which coin is dragging things down", "what's the market doing") — but "more breadth" turned out to mean "every candidate ever discovered, and every (candidate, coin) pair's full trade history, in full detail, every single call," which is what actually caused the growth. **This is a real, measured incident, not a hypothetical:** running the historical replay for real discovered that this context had grown to ~10,400 tokens by the time 96 candidates were tracked — a real cost overrun caught only by actually running the system, not by reading the code (see `docs/case_study/methodology-decisions.md`). Fixed by capping the exhaustive parts, not the categories of information:
  - `_trades_by_candidate_summary()` / `_trades_by_candidate_and_coin_summary()` (`replay/judgment.py`) and `build_live_test_summary()` (`context_builder.py`) now keep only the top 15 rows **ranked by `|mean_return|`** — the candidates/pairs most worth a human's attention either way (best or worst), never an arbitrary or alphabetical cut — with a note pointing to `/summary`/`/replay_summary` when the list was truncated.
  - `_all_candidates_status_summary()` (`replay/judgment.py`) collapses the `insufficient_data` bucket (usually the large majority — 67 of 96 tracked candidates in one real measurement) into a single count-plus-name-list line instead of one detailed line each, since there's rarely anything candidate-specific to say about a trigger that simply hasn't fired enough times yet. `accepted`/`watch`/`rejected`/`dropped` candidates — the ones a question is actually likely to be about — keep full detail, uncapped.
  - **Deliberately not capped:** the "already tested via 'test it' and not accepted" name list `build_context_summary()` (`context_builder.py`) gives Sonnet. This one is functional, not just informational — it's how Sonnet avoids re-proposing a condition a human already tested. Capping it risks a real regression (a duplicate proposal), unlike the other two lists, which exist purely for a human's convenience and have a free local alternative.

  Measured on this project's own real, accumulated state (96 tracked candidates, 1,728 logged live tests): **~10,400 tokens before this fix → ~2,700 tokens after (-74%)**, and now bounded — it will not keep growing as more candidates get discovered or more live tests resolve, because every uncapped block above has a hard ceiling.

**Why this covers every question, not just the ones anticipated in advance:** nothing is omitted *categorically* — Sonnet still sees the full picture at summary level (every candidate's status, every candidate's aggregate performance, current prices, open/closed test counts) on every single call. Only the exhaustive *tail* of per-row detail is capped, and only past the point where a human is realistically going to ask about that specific row: a candidate or pair with a huge |mean_return| (good or bad) is exactly the kind of thing worth asking about, and is guaranteed to survive the top-15 cut; a candidate sitting at N=2 with a near-zero return is unlikely to be the subject of a question, and if it genuinely is, the truncation note tells the reader (and Sonnet) exactly where to get the complete list instead of guessing or silently omitting it.

**For genuinely exhaustive questions, the answer is a free command, not a bigger LLM prompt.** `/summary` and `/replay_summary` (`telegram/bot.py`, via `format_trigger_summary()` in `candidates/methodology.py`) recompute the full battery fresh on demand — real statistics, no LLM call at all, no truncation, no cap — and cost **$0** in API terms (measured: ~4.4 seconds of local computation for 38 tracked candidates). The design split is deliberate: Sonnet answers *"what does this mean, why, what should I make of it"*; the local commands answer *"give me everything, exhaustively"* — the two questions don't need the same context budget, so they don't share one.

**A related correctness fix that's also a cost fix:** every Sonnet call in this project sets `max_tokens=2000` (not the 700-800 first used), after live testing showed the model spending an unpredictable, sometimes-large share of its output budget on an unrequested "thinking" block, occasionally leaving too little room for the actual JSON/text answer and truncating it (`stop_reason="max_tokens"`, observed live, not theoretical). A truncated call that then needs a retry effectively doubles its own cost; the fixed budget avoids that failure mode outright rather than paying for it via retries.

### 🚀 Part 2 — Running Live, Ongoing Cost (Anthropic API Only — Excludes Any Dedicated Server/Hosting)

This is the recurring monthly cost once the system is actually deployed and left running — **API usage only**. Keeping the hourly/weekly jobs alive 24/7 needs a host of some kind (a small VPS, a scheduled cloud job, etc.); that cost is separate and not estimated here.

Production's own escalation calls (`sonnet_strategist()` / `sonnet_shock_response()`) were measured directly against real production state and come to **~1,400 tokens/call** (~$0.01/call) — smaller than the Q&A path ever was before Part 1's fix, since they were never affected by that growth in the first place (they never call `build_live_test_summary()`, only the small, bounded `build_context_summary()`). This figure will drift up slowly as production accumulates real dynamic candidates over months (the "already tested" name list in `build_context_summary()` is deliberately uncapped, see Part 1), but stays name-only, not full-detail, so the growth is slow.

Hourly shock scan (Sonnet only called on an actual detected shock, rare) + hourly headline screening (Haiku, cheap, batched) + a handful of escalations/day + occasional weekly keep/drop or milestone advice ≈ **$5-10/month** in moderate activity, likely under $20/month even in an unusually volatile month — a small fraction of Part 1's own replay cost, which compresses years of events into a short, continuous burst and is not representative of live, one-event-at-a-time operation.

### 🖥️ Part 3 — Server / Hosting Cost Optimization (What Stays Off the Live Host)

The live host only needs to run the cheap, real-time-sensitive jobs continuously: the hourly mechanical trigger scan (`execution/live_testing.py::run_once()`, pure pandas/statistics, no LLM), the hourly shock/headline scans (API calls only, no local compute), and the always-on Telegram bot loop (`telegram/bot.py::run_bot()`, idle almost all the time). None of these need meaningful CPU or memory — a minimal VPS handles all of them comfortably.

**One genuinely heavy periodic job is deliberately kept off the live host: `execution/hyperopt_runner.py`.** It was built local-only from the start (see its own module docstring), for reasons that hold up under measurement, not just intent:
- **It's the one real compute cost in this project.** A single candidate at 50 epochs of Freqtrade's Bayesian hyperopt took several real minutes in this project's own testing — compare to the entire weekly candidate battery re-run (`run_all()` / `run_replay_battery()`), which is genuinely cheap: **4.4 seconds measured, for 38 tracked candidates.** Running hyperopt on a growing candidate registry (the historical replay alone reached 96) on a paid, always-on host would be paying 24/7 pricing for a workload that's actually bursty and occasional.
- **It never needs to be fresh.** `classify_status()` never reads its output — it's a second, independent opinion shown alongside the project's own walk-forward numbers, purely informational (see "Freqtrade hyperopt cross-check" in `docs/case_study/methodology-decisions.md`). TP/SL multipliers optimized a month ago are still perfectly usable; nothing downstream blocks on this being current.
- **Its output is one small file.** `execution/hyperopt_results.json` is the only thing that needs to reach the live host — run the cross-check locally (`python3 -m execution.hyperopt_runner`, from the project root; add candidate labels to run only those, `--epochs`/`--timerange` to override the defaults — weekly, monthly, whenever convenient, no cadence is load-bearing) and copy or push that one file over. No sync infrastructure, no shared database, no server-side Freqtrade install at all.

**What this does *not* apply to:** the weekly candidate battery refresh itself (`scheduler/weekly_revalidation.py`) is real compute, but small enough (seconds, not minutes, even at dozens of candidates) that there's no real hosting-cost incentive to move it off the live host — doing so would only add sync complexity (its output, unlike hyperopt's, actually gates what the live system treats as `accepted`/`watch`/`rejected`) for a cost saving too small to matter.

## Trade Execution (Phase 2, Module B) — `execution/`

This project never opens a funded position (see [methodology-decisions.md](docs/case_study/methodology-decisions.md)) — the files below are grouped by which of the two live models they belong to.

**Live testing (the actual current model — no TP/SL, no funded position):**
- **`live_testing.py`** — Production's real-data counterpart to `replay/engine.py`'s day-by-day walker: `_open_live_test()`/`_check_live_tests()` (hold for the horizon `pattern_significance` found significant, resolve by measuring real forward return/MFE/MAE), `_scan_mechanical_triggers()` (unattended, no LLM, hourly detection, precomputed on the full series before slicing — same lookback-starvation fix as the replay), `find_backdated_entry()` (retroactively anchors a newly-discovered condition's own triggering occurrence to the real hour it first became true, using already-recorded price history — never something a funded order could do, legitimate here since nothing real is ever placed), `check_n50_milestones()` (production's own recurring N=50 checkpoint, `PRUNE_KEYBOARD_TEMPLATE` buttons, wired from `scheduler/weekly_revalidation.py`) plus `_effective_milestone_count()` (mirrored identically in `replay/engine.py`) — what counts toward the 50 differs by how a candidate was found: static candidates (C1/C2/C6) require 50 real (or, in the replay, simulated) live occurrences only, since they were derived by directly mining this project's own historical data; dynamic (Sonnet-proposed) candidates instead use a rolling window of the most recent 50 occurrences, backtest and live mixed, since Sonnet never sees this project's own backtest results before proposing (only a live snapshot) — a much weaker, diffuse contamination risk than the static candidates' direct one. The rolling window only decides *when* a checkpoint fires, never what `pattern_significance` itself computes over. Once a dynamic candidate accumulates 50 real live occurrences on its own, backtest stops contributing and it follows the exact same live-only rule the static candidates always have (see docs/case_study/methodology-decisions.md). `_check_consecutive_failures()` (fires inside `_check_live_tests()`, immediately after each live test resolves, only for a VALIDATED candidate — a fast, purely informational early-warning when its last `CONSECUTIVE_FAILURE_ALERT_THRESHOLD=2` (or more) resolved live tests all came back negative, showing the last `max(streak, 5)` occurrences and their mean return/MFE/MAE ratio for context; never changes any candidate's status — see docs/case_study/methodology-decisions.md for why a well-established candidate's own aggregate statistics are, by design, far too slow to react to a real regime change on their own). `run_once()` (entry point for a scheduled job: resolves due live tests, then scans every tracked trigger).
- **`live_test_state.py`** — Persistent state for the above (`live_tests.json`, `horizons.json`) — mirrors `replay/state.py`'s equivalent subset against real, not simulated, data.
- **`hyperopt_runner.py`** / **`freqtrade_bridge.py`** / **`freqtrade_userdir/strategies/hyperopt_candidate_strategy.py`** — A periodic, local-only, purely informational cross-check (see "Cost Optimization" Part 3 above): runs Freqtrade's own (independent) Bayesian hyperopt against this project's real data to re-derive TP/SL multipliers for each tracked candidate. `python3 -m execution.hyperopt_runner` from the project root is a real CLI (`--epochs`/`--timerange`, specific candidate labels, or every tracked candidate by default) — writes `execution/hyperopt_results.json`, the one file that needs to reach a live host. `freqtrade` is imported lazily (inside function bodies) so nothing else in this project gains a hard dependency on it. `_run_one()` never returns a bare failure — every attempt is persisted as `{"status": "ok", ...}` or `{"status": "failed", "reason": ..., "at": ...}`, so a failed or data-starved run is distinguishable from "never attempted."

**Superseded (kept, not deleted — the underlying TP/SL/anchor machinery is what the hyperopt cross-check above now reuses):**
- **`strategies/sentiment_agent_strategy.py`** — The Freqtrade `IStrategy` implementation this project's live execution used before the live-testing model above. Not currently loaded for live trading.
- **`signal_store.py`** — Bridge between the LLM layer and the strategy above: a pending/active signal split so an approval is consumed exactly once and its anchors stay recoverable at exit time, days later.
- **`config_live.json`** — Freqtrade configuration for the strategy above: futures/isolated margin mode, dry-run, 7-coin pair whitelist.

## Telegram Interface (Phase 4) — `telegram/`

- **`bot.py`** — The long-polling bot process (`run_bot()`). `_send(text, reply_markup=None, pin=False)` — `pin=True` best-effort pins the message (used by `/help`, no special permission needed in this bot's private 1:1 chat). Commands (special-cased before the generic dispatch, none touch an LLM): `/summary` (production's `format_trigger_summary()`, fresh, real), `/details <name>` (`candidates/methodology.py::format_candidate_details()` — the full numeric breakdown one candidate's `/summary` line deliberately omits to stay short: the trigger's own exact numeric definition via `_trigger_numeric_description()`, N, p-value, excess return, MFE/MAE ratio, coin/year concentration percentages, reference TP/SL backtest stats, and `explain_non_acceptance()`'s reason if not accepted), `/replay_summary`/`/replay_details`/`/replay_status` (same three for the replay), `/help`/`/start` (pinned reference: every command, plus the local-only hyperopt CLI's own reference text), `"replay continue"` (advances the replay). `_trigger_numeric_description(candidate)` mirrors `_trigger_description()`'s static/dynamic lookup but returns `candidates/definitions.py::TRIGGER_NUMERIC_DEFINITIONS` (the precise thresholds behind each static trigger, e.g. "funding z-score below -2.0" vs. `TRIGGER_DESCRIPTIONS`'s prose-only "an extreme funding rate") or, for a dynamic condition, the same `condition_desc()` output (which already carries its own numeric threshold). Button callbacks: `handle_propose_callback()`/`handle_replay_propose_callback()` (Test It / Don't Test It, id-addressed for production, single-slot for the replay), `handle_prune_callback()`/`handle_replay_prune_callback()` (Keep Testing / Drop from Batch), `handle_kpi_callback()` (superseded, see below). Free text falls through to `handle_natural_language()` (Sonnet, grounded only in real computed numbers — never invents a price, a percentage, or a live-test detail).
- **`kpi_queries.py`** — Superseded: real SQL queries against a Freqtrade trade database (win rate, Sharpe, Sortino, max drawdown). Under the current no-funded-position model, no Freqtrade order is ever placed, so this database never receives a real entry — `/summary`/`/replay_summary` are the current equivalent for real reporting.

## Scheduling (Phase 3) — `scheduler/`

- **`live_daemon.py`** — The single real entry point for running this project live: `python3 -m scheduler.live_daemon`, one process, no external cron. Owns the Telegram long-poll loop itself (the same `_get_updates()`/`_dispatch_update()` pair `telegram/bot.py::run_bot()` uses standalone) and, between polls, checks elapsed time against a persisted `live_daemon_state.json` (gitignored — real runtime state, not a durable record) to decide whether it's time to run the hourly jobs (`live_testing.run_once`, `haiku_sonnet_pipeline.run_once`, `run_shock_scan`) or the weekly one (`weekly_revalidation.run_weekly_revalidation`). Each scheduled job runs through `_run_isolated(name, fn, alert_on_failure=True)` — one job crashing sends a Telegram alert and is retried on its next normal cycle, never taking the whole daemon down; `alert_on_failure=False` for weekly re-validation only, since it already sends its own more specific alert internally before re-raising (avoids double-reporting the same failure). The daemon's own `_get_updates()` call is wrapped in try/except too (a gap `telegram/bot.py::run_bot()` alone still has, documented below) — a network blip during polling backs off and retries rather than crashing the process. State persists across restarts, so a restart doesn't immediately re-fire a job that already ran recently.
- **`weekly_revalidation.py`** — Refreshes market/funding data first, then re-runs the full candidate battery, diffs every candidate's status against the previous run, notifies on change, notifies separately on any candidate's `horizon_changed_to` (set by `run_battery.py` whenever a fresh `pattern_significance` run empirically derives a different horizon than last time), calls `check_n50_milestones()` (production's recurring validation checkpoint) and handles the 2-year keep/drop safety net (`explain_non_acceptance()` gives the specific reason shown to the human, not a generic line) and the shutdown flow. Written and tested end-to-end; run automatically once a week by `live_daemon.py`, no external cron job needed — can still be run on demand directly for testing. Any crash past the data refresh sends a Telegram alert before re-raising, so a silent failure is never indistinguishable from an ordinary "nothing changed" week.

## Partial Failures & Crashes

What happens when something breaks mid-run, and what still doesn't handle it:

- **`candidates/run_battery.py`** — each candidate (static or dynamic) runs in its own try/except. A failure shows up as `status = "error"` in that week's table and in `meta["failed_candidates"]`, and is retried automatically next run — it does not touch that candidate's `status_history.json` entry (no real verdict was reached) and does not cost any other candidate its result.
- **`data_ingestion/market_data/binance_fetcher.py`** — same isolation per coin: one coin's OHLCV or funding fetch failing (`None` in the report, not `0`) doesn't block the other six.
- **`llm_pipeline/haiku_sonnet_pipeline.py::run_once()` / `run_shock_scan()`** — each escalated headline or detected shock is isolated; a malformed model response for one item is logged and skipped, the rest of that run still gets processed. The two functions are also isolated from EACH OTHER in `__main__`, so one failing doesn't prevent the other from running.
- **`scheduler/weekly_revalidation.py`** — the one process-level alert: any exception past the (already-lenient) data refresh sends a Telegram message describing the failure before re-raising. Without this, "no message this week" was ambiguous between "nothing changed" (normal) and "the whole run silently died" — indistinguishable to the human either way.
- **`execution/hyperopt_runner.py`** — a failed or data-starved run is persisted as `{"status": "failed", "reason": ...}`, distinguishable from "never attempted" — not silently swallowed.
- **`llm_pipeline/pending_tests.py`** — proposals expire after 48h rather than sitting in the queue indefinitely if a Test It / Don't Test It button is never pressed.
- **`scheduler/live_daemon.py`** — each scheduled job (`_run_isolated`) is isolated the same way as the loops above, and its own `_get_updates()` call is wrapped in try/except too — a network blip backs off and retries rather than crashing the process.
- **`telegram/bot.py::run_bot()`** — its long-poll loop wraps `_get_updates()` in try/except too (10s backoff, then retries), not just the per-update dispatch. Previously a real, documented gap — closed after it actually crashed the process live: a stray extra `getUpdates` call from outside the loop (Telegram allows only one active long-poll per bot token) returned an HTTP 409 Conflict on the next poll, which was unhandled and killed the whole process. See docs/case_study/methodology-decisions.md.
