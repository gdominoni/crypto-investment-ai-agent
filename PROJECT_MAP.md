## Backtesting Methodology (Phase 1) — `candidates/`

- **`methodology.py`** — Core statistical engine, shared by every candidate (static and dynamic, production and replay). `build_events()` (causality-safe entry, always the bar after a trigger), `pattern_significance()` (**the actual acceptance gate**: walk-forward per-fold horizon selection, then a 2,000-resample bootstrap test of the held-out forward return against that coin's own unconditional baseline over the same calendar stretch, plus the MFE/MAE risk-path ratio). **Both halves of that test were rewritten by the 2026-08-29 audit and the details matter** (full reasoning + measurements in `docs/case_study/methodology-decisions.md`): the horizon is selected by **signed, standardised excess over the period-matched baseline at that same horizon** — signed because `abs()` could pick a horizon precisely *because* the effect was strongly negative for a `long` candidate, and excess-over-baseline because scoring the raw mean was a measured drift bias: mean forward return grows monotonically with horizon across this universe (0.19% at 1d to 12.10% at 45d), so "highest mean return" was very nearly "longest horizon offered". The narrow 1–21 grid masked it; widening to 45 made all seven folds pick 45 and made the p-value *worse*. Standardising by the event returns' own SD then makes horizons comparable (excess grows ~linearly in h, noise only ~sqrt(h)). Verified against ground truth: a signal planted at a 7-day horizon is now chosen at 7 in every fold on both grids and the p-value is a **pre-specified upper tail in the traded direction** (was a tail chosen after seeing which way the effect went — a two-sided procedure priced as one-sided, which let four of six static candidates be "significant" with a negative excess return). Resampling is a **moving-block** bootstrap (`_block_bootstrap_means`, blocks of `BASELINE_BLOCK_HORIZON_MULTIPLE=3` x horizon, drawn within a chunk and never across a boundary) because the baseline's overlapping forward-return windows are serially dependent — measured under a true null, i.i.d. resampling rejected at **43.3%** against a nominal 5%; the block version at 8.7%, and that residual is stated rather than rounded. Returns `oos_events` (per-event group/period/forward_return, so concentration can be measured on the same quantity the gate reads), `p_value_two_sided` (diagnostic only, never the gate), and `horizons_used` (MFE/MAE is aggregated **per fold at that fold's own horizon** then averaged, never pooled raw across folds, since excursions scale with sqrt(horizon)). `basket_forward_returns()`/`_market_adjust()`/`_market_adjust_array()` (the market-relative measurement, applied to the treated events AND the baseline together -- adjusting one but not the other would make the market's own drift appear as excess return and every candidate look like a discovery). `benjamini_hochberg()` also takes optional **`weights`** for prior-weighted FDR (Genovese, Roeder & Wasserman 2006): weights are normalised to mean 1 so the error budget is REDISTRIBUTED, not enlarged -- marking every hypothesis highly plausible therefore achieves exactly nothing, and promoting one makes the rest of the family strictly harder. Measured in simulation at this project's own family size and power: even a weak prior (correlation 0.2 with the truth) yields ~45% more true discoveries, and realised FDR stays at or under alpha at every prior quality, so a useless prior is wasteful rather than dangerous. `benjamini_hochberg()`/`apply_fdr_demotion()` (family-level multiplicity control, run as a second pass after every candidate in a run has a p-value, because BH is inherently a family decision; **demotion-only** -- BH is at least as strict as raw p<alpha so it can remove a candidate from `accepted` but never add one, and a demoted candidate is dropped from `live_state` so it cannot open live tests; validated against the canonical Benjamini & Hochberg 1995 worked example and cross-checked against scipy). `pattern_significance`'s `baseline_events` parameter selects WHICH QUESTION is asked: without it the baseline is the coin's unconditional forward returns ("does anything happen after this at all"), with it the baseline is the SAME condition minus its event clauses ("does the event ADD anything given the market state") -- reported as `baseline_kind`, because `+1.09% p=0.356` unconditional and `-0.23% p=0.483` incremental were the two answers for one real condition and must never be worded identically. `classify_status()` (turns a report + concentration check + pattern result into `accepted`/`watch`/`rejected`/`insufficient_data`, in that exact branching order — concentration is checked *before* significance, a real bug once inverted; it now also independently re-checks `excess_return > 0` as belt-and-braces against a wrong-direction pattern, and treats `concentrated is None` as "cannot assess" → `watch` rather than a pass, see `docs/case_study/methodology-decisions.md`), `explain_non_acceptance()` (the SPECIFIC reason a candidate isn't `accepted`, mirroring `classify_status`'s own branching — never a generic or misleading line), `STATUS_PLAIN` (plain-English gloss for each status code), `format_trigger_summary()` (powers `/summary`/`/replay_summary` — groups every tracked candidate by status, capped/compacted so the message never grows unbounded), `format_candidate_details()` (powers `/details`/`/replay_details` — the full numeric breakdown for one named candidate: N, p-value, excess return, MFE/MAE ratio, coin/year concentration percentages, reference TP/SL stats, `explain_non_acceptance()`'s reason if applicable, and — a real gap fixed after being caught live: whether the candidate is `VALIDATED`, from its `all_latest_statuses()` entry — `status` (accepted/watch/rejected) and `validated` are different claims, see "accepted vs validated" below, and the two were never shown together in this one command until this fix, even though a candidate can be both `accepted` and already `VALIDATED` at once; takes the trigger's own definition string, current holding horizon, and milestone info as parameters rather than looking them up, so this module gains no dependency on `candidates/definitions.py`, the dynamic-condition registry, or either production's/replay's own live-test-state or status-history module), `path_outcome()` (the live-test resolution primitive: forward return + MFE + MAE for one real occurrence, the same convention `pattern_significance` uses), `compute_anchors()`/`walk_forward()`/`report()` (duration-bucketed TP/SL levels and the informational win-rate/Sortino reference stats — no longer gate acceptance, still computed and shown), `concentration_check()` (takes `value_col`, because acceptance is decided on `pattern_significance`'s forward returns while this used to only ever run on `walk_forward`'s TP/SL-conditioned `net_return` — two quantities that genuinely disagree, measured at 96.8% vs 50.0% concentration on identical events; also returns `concentrated=None` for "no positive return anywhere to concentrate", which previously returned `False` and let an all-negative candidate clear both gates), `sortino_ratio()` (returns `+inf` for a candidate with no losing trade at all and `nan` only for genuinely unusable input — collapsing both into `nan` made `classify_status` reject a flawless candidate), `shock_zscore_series()`/`classify_regime()`, `SIGNIFICANCE_ALPHA` (**0.10**, not 0.05 — measured on a synthetic control with known ground truth, raising it lifted detection of real planted effects from 8.3% to 27.4% while the pure-noise arm produced *zero* false positives at either level; the block bootstrap is conservative on overlapping windows, so 0.05 was buying error control the test already gave for free), `required_n_for_power()` (how many events THIS candidate needs before a *null* result from it is informative, from its own realised volatility — deliberately a diagnostic, never an acceptance gate, since the significance test is already calibrated at every sample size), `MAX_GROUP_SHARE` (the single source of truth for the 60% rule — the number previously lived in three places, including a hardcoded `"60%"` string in `explain_non_acceptance`).
- **`definitions.py`** — The three static trigger families, which now serve as the project's **CONTROL ARM** (C1 funding-rate crowding, C2 post-macro-release reaction, C6 efficiency-ratio trend). None contains a real macro-surprise term, so all six variants are rejected by `spec_from_proposal` today — which is the point: they are market-state-only conditions put through identical machinery, and the LLM-discovered conditions have to beat them for this project's thesis to mean anything. They cost no API calls, only the mechanical scan — C3/C4/C5 were part of the prior research's larger set but weren't carried forward), each a pure function of price/volume/funding data. `compute_triggers(df, funding, scale=1)` — `scale=24` reinterprets every day-defined rolling window as its hour-equivalent for the hourly mechanical live-trigger scan (never the backtest, which always uses `scale=1`); `shock_zscore`/`is_macro_day` are the deliberate exceptions that stay calendar/daily-native regardless of `scale`. `TRIGGER_DESCRIPTIONS` (prose, one per base candidate — grounds an LLM call in what a trigger actually tests) and `TRIGGER_NUMERIC_DEFINITIONS` (the same, but with the exact numeric threshold instead of prose, e.g. "funding z-score below -2.0" rather than "an extreme funding rate" — must be kept in sync with `compute_triggers()` by hand, since it's a duplicated description, not a derived one) power `telegram/bot.py::_trigger_description()`/`_trigger_numeric_description()` respectively.
- **`data_loading.py`** — Loads historical OHLCV and funding-rate series from `data/`.
- **`macro_calendar.py`** — FOMC/CPI release calendar, at calendar-day granularity.
- **`macro_vintage.py`** — Point-in-time-correct macro release lookups (`vintage_releases_as_of`, `latest_release_with_prior`, `recent_releases_summary`, `surprise_series`) — a macro figure is only "known" to Sonnet as of its real publication date, never a later-revised value. Shared by production and the replay (`replay/time_sandbox.py` re-exports this module rather than duplicating it). `surprise_series(name, index)` grades HOW FAR a print moved from the previous one (z-scored against the trailing distribution, NaN off release days so the indicator IS the event) -- backing the `cpi_surprise`/`rate_surprise`/`jobless_claims_surprise` whitelist entries. `is_macro_day` alone is binary and cannot distinguish a hawkish shock from a nothing-burger. A degenerate trailing window yields NaN rather than a colossal z-score: real case, the Fed funds rate sits flat for years and a bare `sd > 0` guard produced a "surprise" of -2,613,348 sigma.
- **`run_battery.py`** — Orchestrator: runs every static and dynamic candidate through `methodology.py`, assigns a live status (`accepted` / `watch` / `rejected` / `insufficient_data` / `error`), and writes `execution/live_battery_state.json` (`SIGNAL_STORE_PATH`) — the file everything else reads "what's currently accepted" from. Also re-derives and re-syncs every candidate's horizon (`execution/live_test_state.py::save_horizons()`) every run a pattern-significance result exists for it, independent of accepted/watch/rejected — mirrors `replay/battery.py`'s own sync exactly (a real gap, fixed: this used to only ever be set once, at the moment a human approved a novel condition, never refreshed by the weekly run afterward). `_concentration_for(pattern, oos)` picks the concentration basis: `pattern_significance`'s own per-event forward returns when the test ran, falling back to `walk_forward`'s TP/SL-conditioned `oos` only when it couldn't (where `classify_status` returns `watch` regardless) — mirrored verbatim in `replay/battery.py` and inline in `novel_condition_tester.py`, so all three paths grade concentration on the same quantity the acceptance gate reads. Each candidate is isolated in its own try/except (see "Partial Failures & Crashes" below).
- **`status_history.py`** — Tracks every candidate's status history. Two independent mechanisms: `candidates_due_for_prune_decision()` (2+ calendar years tracked, never once `accepted` — the safety net for a trigger too rare to ever reach its first live-test milestone) and `candidates_due_for_milestone()`/`mark_milestone_reported()` (fires at every new multiple of `MILESTONE_N` in whatever count its caller passes in, not once — this is the ONLY place this project calls a candidate `confirmed`: `accepted` **and** it has kept occurring past that many post-hypothesis occurrences, re-earned fresh at each checkpoint, never a permanent badge. `MILESTONE_N` is 20, tied to `min_report_events`; it was 50 with a comment claiming that same tie, which broke silently when the audit lowered `min_report_events` to 20. The word is `confirmed` and not `validated` because `required_n_for_power` puts a conclusive test at 307 occurrences over 7 days and 742 over 14 — no reachable count demonstrates an effect of interesting size, so the checkpoint asserts persistence; stays fully origin-agnostic itself — see `_effective_milestone_count()` in `execution/live_testing.py`/`replay/engine.py` for what actually gets counted and why it differs by static vs. dynamic). `record_horizon()` tracks the empirically-derived holding horizon per candidate, notifying on its first real value or any later change.

## Historical & Market Data — `data/`

- OHLCV data (daily/hourly) for 7 coins (BTC, ETH, BNB, XRP, DOGE, ADA, LTC) from Binance spot, funding-rate history, and macro series (CPI, Fed funds rate, initial jobless claims) from FRED. Coverage: from each coin's real listing date through the present — kept current by `data_ingestion/market_data/binance_fetcher.py` below, not a frozen snapshot. Exactly these 7 coins everywhere in the repo (a prior attempt at SOL/AVAX/LINK was tried and excluded — see `run_battery.py`'s own docstring — and their leftover data files were removed rather than left stale and unfetched).

## Live Data Refresh — `data_ingestion/market_data/`

- **`binance_fetcher.py`** — `update_ohlcv()`/`update_funding()` pull new candles/funding entries from Binance's public API (no key needed) and append them to `data/`. **Genuinely paginates from a real anchor (`BACKFILL_SINCE = "2017-01-01"`) rather than one bounded call** — a real, fixed bug: Binance's `since=None` returns the *most recent* candles, not the earliest (verified live), so a from-scratch backfill (a new coin, or this repo cloned somewhere `data/` isn't already populated) was silently truncating to ~2.7 years of the newest history instead of full depth, with no error. Now loops until a page comes back short of `limit` (genuinely caught up to "now") or `MAX_FETCH_PAGES` is hit (safety net). `update_all()` isolates each coin's fetch so one failure doesn't block the other six.

## LLM Judgment Layer (Phase 2) — `llm_pipeline/`

- **`haiku_sonnet_pipeline.py`** — The adaptive layer, narrowed to exactly one live escalation role. **The Haiku headline path was REMOVED on 2026-09-02** (`haiku_scout`, `HAIKU_SYSTEM_PROMPT`/`HAIKU_MODEL`, `sonnet_strategist`, `SONNET_SYSTEM_PROMPT`, `run_once`, `format_sonnet_message`, `_asset_to_coin`, and the headline block in the compression prompt all deleted; the module keeps its filename so history stays greppable). Nothing Haiku surfaced could enter a testable hypothesis -- `proposable_indicators()` has no headline/sentiment term and every proposal must carry a FRED macro surprise, so **zero of 771** live tests opened for Sonnet-discovered candidates were ever news-linked. The backfill that would have fixed that was measured, not assumed (`forecast/sentiment_power.py`): at the feed quality real news sentiment achieves (rho=0.04) it accepts 3 conditions of 57 against a pure-noise floor of 2 -- indistinguishable. Removing it also closed a live train/serve gap: production had been showing Sonnet headlines in the compression prompt while the replay's `judge_event` never did, so the two were not answering the same prompt on the primary trigger. `HAIKU_MODEL` now lives in `forecast/model_comparison.py`, its only remaining caller, which asks the separate question of whether Haiku could replace Sonnet as the JUDGE. See `docs/case_study/methodology-decisions.md`. What remains: `sonnet_compression_response()` (Sonnet's judgment for a confirmed exit from a volatility-compression episode, `COMPRESSION_SYSTEM_PROMPT` — the three-phase A/middle/B framing `replay/judgment.py::format_compression_event()` builds, shared so a hypothesis discovered live and one discovered in the replay answer the same prompt). **The keep/drop and milestone decisions no longer call a model at all**: `candidates/methodology.py::prune_recommendation()` derives them offline from each candidate's own numbers, turning on whether there was POWER to detect an effect (`required_n_for_power`) -- which separates "tested and found nothing" from "never actually asked", a distinction the previous qualitative opinion had no access to. Measured over a 5.5-year replay, that opinion accounted for 665 of 1203 LLM calls (55% of everything spent) to narrate figures the human was already reading. `format_spec_clauses()`/`format_compression_message()` render a proposed condition in plain English (`INDICATOR_PLAIN_NAMES`/`OPERATOR_PLAIN` from `novel_condition_tester.py` — never a raw variable name or a bare `<`/`>` symbol, which was once observed to render as a literal `&gt;` on Telegram). `PROPOSAL_KEYBOARD_TEMPLATE` attaches Test It / Don't Test It buttons to every proposal — replaced an earlier free-text "reply 'test it'" convention that silently did nothing for any phrasing that didn't match one of a few exact strings. `run_compression_scan()` isolates every individual episode in its own try/except — one malformed model response can't silently stop the rest of that run. It handles a proposal SET: `proposals_from_assessment()` normalises the one-or-two-spec schema, `filter_redundant_proposals()` drops a second proposal that fires on the same days as the first, and `push_pending_test()` queues the survivors under one id so one button approves them together.
- **`novel_condition_tester.py`** — `SUPPORTED_INDICATORS` (the full registry) and **`proposable_indicators()`** (the 13 an LLM may actually use — a fixed indicator+operator+threshold grammar, never arbitrary generated code). **`NON_PROPOSABLE_INDICATORS`** holds the four that are registered but barred from proposals, each for its own reason: `shock_zscore` is a price OUTCOME rather than a market state; `vol_compression_zscore` defines the trigger, so it is fixed at every proposal by construction and can discriminate nothing; `is_macro_day` records that a release was scheduled, never what it said; `daily_range_pct` is non-stationary, so a fixed threshold on it selects a YEAR rather than a market state (`>= 0.05` takes 62% of 2021 and 16% of 2026 — `range_zscore_30d` is its usable form). All four stay registered so the committed sweeps in `forecast/` remain reproducible. The prompts' whitelist is DERIVED from `proposable_indicators()` rather than written by hand, after the two drifted and the system spent real money on proposals its own instructions requested and its own validator refused. **`MAX_PROPOSABLE_CLAUSES = 2`** and **`MAX_PROPOSALS_PER_CALL = 2`**: each extra clause divides historical occurrences by roughly eight (median 1172 / 139 / 12 at one, two and three clauses), so a deeper conjunction is replaced by two separate 2-clause hypotheses — measurable where their conjunction is not. **`filter_redundant_proposals()`** then drops a second proposal that is one hypothesis wearing two hats, judged on BEHAVIOUR (`behavioural_agreement()`, the Jaccard overlap of the days two specs fire on) and never on shared clauses: the intended pattern is two proposals sharing their news term, whose measured overlap is 0.000. **`is_testable()`** applies both floors in one place — `MIN_HISTORICAL_OCCURRENCES = 120` raw firings (whether a walk-forward test can RUN at all: 90% of conditions with 35-60 returned `insufficient_data`) and `MIN_HISTORICAL_EPISODES = 40` via **`episode_count()`** (whether the result MEANS anything: `build_events` makes one row per triggered bar, so a `within_days` lookback produces up to 8x the firings for 1.7x the independent evidence, 79% of them overlapping). **`relax_to_testable()`** loosens a too-rare condition toward measurability instead of discarding it, moving each threshold toward that indicator's neutral point (`RELAXATION_NEUTRAL`) and never across it — the naive percentage-of-magnitude version turned "overbought, RSI >= 70" into RSI >= 52.5 and flipped "cool CPI, surprise <= 0" to match hot prints. The search criterion is the occurrence count and nothing else, which is what makes it a power calculation rather than p-hacking, `INDICATOR_PLAIN_NAMES`/`OPERATOR_PLAIN` (plain-English translation for every indicator and comparison shown to a human), `test_novel_condition()` (runs a proposed condition through the exact same `methodology.py` pipeline as the static battery, including the same shock-regime exclusion unless the condition being tested IS the shock indicator itself), `condition_desc()`/`format_pattern_significance()` (shared rendering used by every message that shows a tested condition). **`Clause.within_days`** makes an ORDERED hypothesis expressible: 0 (default) = true on the trigger bar, K = true at any point in the last K days -- the grammar could previously say "news AND crash the same day" but not "crash, THEN news", the central case this project is about; rendered explicitly to humans so the two never read identically. **`EVENT_INDICATORS`/`reduced_spec()`** split event clauses (macro surprises, shock, macro-day) from market-state clauses and build the control condition for the incremental test above. **`DAILY_NATIVE_INDICATORS`** is a real train/serve fix: four indicators (`rsi_14d`, `atr_pct_14d`, `daily_range_pct`, `efficiency_ratio_20d`) are NOT distributionally comparable at `scale=24`, so a condition accepted on `rsi_14d < 35` (289 daily occurrences) fired ZERO times in the live hourly scan -- a 336-period RSI mean-reverts to ~50 and never reaches the threshold, making the candidate look merely rare rather than broken; `shock_zscore` already had this exception hardcoded, it was just never generalised. Both hourly scanners now delegate to the single shared `clause_signal_hourly()`. **`clause_to_dict()`/`clause_from_dict()`** are the only serializer/deserializer pair (all three call sites previously dropped `within_days`, so a sequenced condition round-tripped back as a same-day one), the latter doubling as the sanitiser for model-produced JSON. **`ConditionSpec` now DECLARES three things up front, not after seeing results.** **`coins`** scopes a hypothesis to the assets it is actually about (an XRP lawsuit is a fact about XRP; testing it on DOGE adds noise, not evidence) and intersects with the caller's universe rather than replacing it. **`outcome`** picks what the forward return is measured against: `raw` for a market-wide event (a CPI print moves all of crypto, so subtracting the market would delete the effect being tested) or `market_relative` for a coin-specific one (mean cross-coin correlation is 0.54, so most of any coin's move IS the market's -- removing it removes mostly noise; measured 2/9 -> 6/9 accepted on a coin-specific planted signal, and 10 -> 7 on a market-timing one, which is why it can never be a global switch). **`prior_weight`** (0.25-4.0) is proposal-time plausibility feeding prior-weighted Benjamini-Hochberg. All three are declared BEFORE the test runs -- choosing any of them after seeing which measurement scored better would be picking the answer. **`spec_to_dict()`/`spec_from_dict()`** are the single serializer pair, replacing seven hand-rolled versions: every field ever added to `ConditionSpec` has been dropped by at least one of them, and `within_days` was lost by all three at once, so a sequenced "crash, THEN news" hypothesis round-tripped back as a same-day one. Defaults are omitted so existing registry files don't churn, and dicts written before these fields existed still load. **Every indicator now takes `symbol`** -- almost all ignore it (RSI does not care what it is computing on), but without it a news or sentiment score attributed to one coin cannot be written at all: the first single-coin test had to identify XRP by its price series LENGTH. **`build_indicator_leadup()`** gives Sonnet a day-by-day table of the last 7 days rather than a single instant -- without it the model cannot tell "the crash was three days ago" from "both happened today" and so cannot sensibly choose a `within_days` at all.
- **`shock_detector.py`** — **DELETED 2026-09-05.** It held `scan_for_shocks()`, the escalation path `compression_detector.py` replaced. Its entry in this file used to claim the classification survived and was "still used to tag regimes and to exclude extreme events from the static battery's fitting" -- that was not true: nothing imported the module, `current_shock_status` had no callers at all, and the regime tagging is done by `candidates/methodology.py::classify_regime`. Its `SHOCK_ZSCORE_THRESHOLD` was independently defined in `run_battery.py` and `novel_condition_tester.py`, so nothing depended on it either. Kept alive by a justification that had stopped holding. The reasoning that retired the shock trigger is in `docs/case_study/methodology-decisions.md` and in `compression_detector.py`'s own docstring, which is where a reader looks for it.
- **`compression_detector.py`** — The market-data escalation path that replaced it. `current_compression_exit()`/`scan_for_compression_exits()` find coins whose unusually quiet period has just ended, calling `candidates/methodology.py::compression_exit()` — the exact function the replay triggers on, so "compression exit" is one definition rather than two that drift. Keeps a ledger keyed on the EXIT date (`already_escalated`/`mark_escalated`), which is what stops an hourly daemon asking the same question twenty-four times.
- **`context_builder.py`** — `build_context_summary()` (currently-accepted candidate names + the "already tested via 'test it' and not accepted" name list — deliberately never capped, since Sonnet needs it to avoid re-proposing a duplicate). `build_live_test_summary(top_n=15)` (by-candidate and by-candidate-and-coin live-test performance, capped at the top 15 rows by `|mean_return|` with a pointer to `/summary` for the rest — fixed after a real measured incident where this context grew to ~10,400 tokens at 96 tracked candidates; see "Cost Optimization" below). `build_technical_snapshot()` queries a Freqtrade SQLite trade database for "open positions"/"last closed trade" — a holdover from the superseded execution model (see "Trade Execution" below); since no funded position is ever placed under the current model, this table never receives a real entry.
- **`dynamic_candidates.py`** — Persistent registry of conditions discovered live (`record_test_result()`, called regardless of verdict — accepted, watch, or rejected — so a rejected condition isn't silently re-proposed and an accepted one isn't trusted forever from one test), re-tested weekly alongside the static candidates by `run_battery.py`.
- **`pending_tests.py`** — FIFO queue of novel-condition proposals, each with its own short `id` embedded in that proposal message's own Test It / Don't Test It buttons (`push_pending_test()` returns the id; `pop_pending_test_by_id()`/`discard_pending_test_by_id()` resolve or dismiss the *exact* proposal a button was pressed on — never "whichever one happens to be oldest," which is what the earlier free-text design did). Entries expire after 48h so an unanswered proposal doesn't sit forever.

## Historical Replay — `replay/`

A day-by-day walker through real 2017-present history, entirely isolated from production's own state (`replay/state/`, gitignored, never shared with `candidates/status_history.json` or any file under `execution/`). Same statistical methodology and live-test model as production, run against real historical data compressed into a short, continuous burst — used to validate the methodology and build an initial live-test track record before actually going live, and this project's own primary demonstration mechanism. Real run so far: reached 2023-06-04 from a 2017-08-26 start (stopped only by Anthropic credit exhaustion, not a bug — checkpoint resumes cleanly), 96 tracked candidates (6 static + 90 discovered live via Sonnet proposals), 1,728 live tests opened, 1,714 resolved.

- **`battery.py`** — `run_replay_battery(as_of)`: mirrors `candidates/run_battery.py` exactly, sourced entirely from as-of data (`time_sandbox.py`) instead of full history, so a status computed on a given simulated day can never see data from after it.
- **`judgment.py`** — `judge_event()` (Sonnet's judgment for one confirmed compression exit — the same narrow, bounded context production's `sonnet_compression_response` uses; takes a `model` parameter used only by `forecast/model_comparison.py`), `format_compression_event()` (the three-phase A/middle/B narrative, with every macro release during the squeeze rendered as a CHANGE from the prior print and a SURPRISE in standard deviations, never as a bare level — `_macro_during()`), `answer_market_question()` (free-text Q&A, `_trades_by_candidate_summary()`/`_trades_by_candidate_and_coin_summary()` capped at top 15 by `|mean_return|`, `_all_candidates_status_summary()` compacting the `insufficient_data` bucket to a count-plus-name-list — the same fix as production's `context_builder.py`, for the same reason), `format_telegram_message()` (mirrors production's proposal message format exactly, no "this is a simulation" framing inside the message body).
- **`engine.py`** — `advance(chunk_days)`: the actual day-by-day walker, halts (`checkpoint.status = "waiting_for_human"`) whenever a novel-condition test is proposed until `resolve_pending_test()` (Test It) or `discard_pending_test()` (Don't Test It) is called, via `REPLAY_PROPOSAL_KEYBOARD`. `_open_live_test()`/`_check_live_tests()` (no TP/SL, holds for `pattern_significance`'s own horizon, resolves via `path_outcome`), `_scan_mechanical_triggers()` (unattended, hourly-resolution detection — `_static_triggers_full` precomputed once per chunk on the *full* hourly series, not a sliced window, after a real bug where slicing first starved rolling-window indicators of their lookback and silently produced all-NaN/False), `_compression_exit()` (the replay's only trigger — a confirmed exit from a volatility-compression episode, aliased to `candidates/methodology.py::compression_exit()` so production cannot drift from it), `_prepare_proposal()`/`_cooccurrence_appendix()` (the latter reports how often two proposals have historically fired together, as a COUNT and never an outcome statistic, listing every pair and opening no test — it is a note attached to two real results, not a third candidate), `_check_prune_decisions()`/`_check_n50_milestones()` (the same two keep/drop mechanisms as `candidates/status_history.py`, driven by the replay's own simulated clock instead of real wall-clock time), `_check_consecutive_failures()` (mirrors `execution/live_testing.py`'s own version exactly — a fast, informational-only losing-streak alert for VALIDATED candidates only), `_send_checkpoint_digest()` (a status summary every ~30 simulated days).
- **`state.py`** — Replay's own isolated state store: `checkpoint.json` (simulated date + run status), `battery_status.json`, `trade_log.json`, `dynamic_candidates.json`, `pending_test.json`, `horizons.json`, and a deferred-reveal queue (`queue_reveal()`/`due_reveals()` — a "test it" result surfaces on its own scheduled day, not instantly, so a rapid string of simulated messages still reads as a coherent history spread over real calendar time).
- **`status_history.py`** — Same two mechanisms as `candidates/status_history.py` (2-year prune safety net, recurring `MILESTONE_N` confirmation checkpoint), keyed off the simulated `as_of` date instead of `datetime.now()`.
- **`post_replay_hyperopt.py`** — The Freqtrade cross-check, run ONCE after a replay finishes rather than inline. `hyperopt_runner` optimises over the whole history to the present, so a message dated 2020 quoting it would show 2026 data — an artefact of compressing nine years into hours, not a property of the system (live the two coincide). Inline it would also add 10-16 hours to a run whose entire API cost is about \$7.
- **`state.py`** — also holds the two stores the confirmation path needs: `parked_proposals.json` (well-formed, on-thesis proposals whose history has not yet reached the testability floor — re-checked daily, at the top of `advance()`'s own loop, not the weekly battery refresh where this used to sit; promoted oldest-first, one per day) and `confirmation_priors.json` (per candidate, how many occurrences already postdated its hypothesis at registration).
- **`time_sandbox.py`** — `daily_as_of()`/`funding_as_of()`: slices real market data to "as of this simulated date," the mechanism that makes the whole replay causality-safe. Re-exports `candidates/macro_vintage.py` rather than duplicating it.
- **`orchestrator.py`** — `run_to_completion()`: a batch driver that repeatedly calls `advance()`.

## Cost Optimization — what actually gets sent to Anthropic

Pricing: **Claude Sonnet 5** $2 / $10 per million tokens (input / output), **Claude Haiku 4.5** $1 / $5, per [platform.claude.com/docs/en/about-claude/pricing](https://platform.claude.com/docs/en/about-claude/pricing). **`llm_pipeline/usage.py` currently prices Sonnet at $3 / $15 instead, and the two cannot both be right.** Flagged rather than quietly reconciled, because it may explain something: `COST_CALIBRATION = 0.735` was fitted by comparing that module's list-price arithmetic against one real invoice, and $2/$10 over $3/$15 is exactly 0.667 — close enough to 0.735 that the "empirical calibration" may be mostly a wrong list price rather than a billing subtlety. Token counts are exact either way; only the dollar column depends on this. Every number below is measured against this project's own real calls and real accumulated state, not a generic estimate.

This section is in three parts, deliberately separated because they answer different questions about money: **Part 1** is the one-time cost of building and stress-testing this case study against nine years of real history (the historical replay) — not something that recurs once the demo exists. **Part 2** is the ongoing, recurring cost of actually running the system live (Anthropic API only). **Part 3** is server/hosting cost, kept separate from both because it's a non-Anthropic line item.

### 🧪 Part 1 — Building & Stress-Testing This Case Study (Backtest / Replay), a One-Time Cost

The historical replay (`replay/`) is this project's own demonstration mechanism — walking a simulated clock through real 2017-2026 history in a short, continuous burst to show how the system would actually have behaved, generating this case study's evidence. It is not part of normal live operation and isn't meant to be re-run routinely; this is the cost of *producing* the case study, paid once (barring a future methodology change big enough to warrant re-validating against history again).

This project's LLM calls split into two kinds with deliberately different context budgets, because they answer two different questions — this split is the actual mechanism behind every number in this section, both here and in Part 2:

**1. Automated per-event judgment** — `judge_event()` (`replay/judgment.py`), `sonnet_compression_response()` (`haiku_sonnet_pipeline.py`). Fires on every confirmed compression exit. Macro releases and volatility shocks were both removed as triggers — a release is one of the CAUSES being sought and a shock is the OUTCOME, and each was measured not to select for what this project looks for (`forecast/trigger_value.py`). That took the replay from ~1,200 judgment calls to 217, about \$3.32. Its context answers one narrow question ("is *this* event worth escalating") and is built to stay **flat regardless of how much history has accumulated**:
  - the one event description (a confirmed compression exit)
  - current indicator readings for the relevant coin(s) only — not a history of past readings
  - macro releases from the last 10 days only — not the full calendar
  - the currently-*accepted* candidate names, one line — not every candidate ever tracked
  - a two-line aggregate stat, not a per-trade history

  Measured real call (a macro event, all 7 coins' indicators): **~1,230 tokens** input, ~$0.01/call at current pricing. This number does not grow as the candidate registry or the live-test log grows — none of its five inputs are keyed to either.

**2. Human-triggered Q&A** — `answer_market_question()` (`replay/judgment.py`), `handle_natural_language()` (`telegram/bot.py`). Fires only when a human asks something free-form on Telegram. This one legitimately needs more breadth, since it has to be ready for *any* question ("what's accepted", "how's candidate X doing", "which coin is dragging things down", "what's the market doing") — but "more breadth" turned out to mean "every candidate ever discovered, and every (candidate, coin) pair's full trade history, in full detail, every single call," which is what actually caused the growth. **This is a real, measured incident, not a hypothetical:** running the historical replay for real discovered that this context had grown to ~10,400 tokens by the time 96 candidates were tracked — a real cost overrun caught only by actually running the system, not by reading the code (see `docs/case_study/methodology-decisions.md`). Fixed by capping the exhaustive parts, not the categories of information:
  - `_trades_by_candidate_summary()` / `_trades_by_candidate_and_coin_summary()` (`replay/judgment.py`) and `build_live_test_summary()` (`context_builder.py`) now keep only the top 15 rows **ranked by `|mean_return|`** — the candidates/pairs most worth a human's attention either way (best or worst), never an arbitrary or alphabetical cut — with a note pointing to `/summary`/`/replay_summary` when the list was truncated.
  - `_all_candidates_status_summary()` (`replay/judgment.py`) collapses the `insufficient_data` bucket (usually the large majority — 67 of 96 tracked candidates in one real measurement) into a single count-plus-name-list line instead of one detailed line each, since there's rarely anything candidate-specific to say about a trigger that simply hasn't fired enough times yet. `accepted`/`watch`/`rejected`/`dropped` candidates — the ones a question is actually likely to be about — keep full detail, uncapped.
  - **Deliberately not capped:** the "already tested via 'test it' and not accepted" name list `build_context_summary()` (`context_builder.py`) gives Sonnet. This one is functional, not just informational — it's how Sonnet avoids re-proposing a condition a human already tested. Capping it risks a real regression (a duplicate proposal), unlike the other two lists, which exist purely for a human's convenience and have a free local alternative.

  Measured on this project's own real, accumulated state (96 tracked candidates, 1,728 logged live tests): **~10,400 tokens before this fix → ~2,700 tokens after (-74%)**, and now bounded — it will not keep growing as more candidates get discovered or more live tests resolve, because every uncapped block above has a hard ceiling.

**Why this covers every question, not just the ones anticipated in advance:** nothing is omitted *categorically* — Sonnet still sees the full picture at summary level (every candidate's status, every candidate's aggregate performance, current prices, open/closed test counts) on every single call. Only the exhaustive *tail* of per-row detail is capped, and only past the point where a human is realistically going to ask about that specific row: a candidate or pair with a huge |mean_return| (good or bad) is exactly the kind of thing worth asking about, and is guaranteed to survive the top-15 cut; a candidate sitting at N=2 with a near-zero return is unlikely to be the subject of a question, and if it genuinely is, the truncation note tells the reader (and Sonnet) exactly where to get the complete list instead of guessing or silently omitting it.

**For genuinely exhaustive questions, the answer is a free command, not a bigger LLM prompt.** `/summary` and `/replay_summary` (`telegram/bot.py`, via `format_trigger_summary()` in `candidates/methodology.py`) recompute the full battery fresh on demand — real statistics, no LLM call at all, no truncation, no cap — and cost **$0** in API terms (measured: ~4.4 seconds of local computation for 38 tracked candidates). The design split is deliberate: Sonnet answers *"what does this mean, why, what should I make of it"*; the local commands answer *"give me everything, exhaustively"* — the two questions don't need the same context budget, so they don't share one.

**Could a cheaper model do the judging? Measured, not assumed — and the answer is no.**
Sonnet judgment is the single largest running cost, so `forecast/model_comparison.py`
tested whether Claude Haiku 4.5 (a third of the price) could replace it. 34 real
compression-exit events, each judged three times — Sonnet twice and Haiku once —
for \$1.21.

The second Sonnet call is the control, not overhead. `temperature=0` is rejected by
the API, so Sonnet is not deterministic: asked the same question twice it does not
return the same proposal. Without knowing that self-agreement there is no scale to
read a Haiku number against, and scoring Haiku against perfect agreement would
condemn it for variance the reference model has too. Agreement is measured
BEHAVIOURALLY — the Jaccard overlap of the days two conditions actually fire on —
because two models never emit the same JSON and matching text would score formatting.

    Sonnet vs Sonnet (ceiling)   mean 0.443   median 0.388
    Haiku  vs Sonnet             mean 0.209   median 0.137
    Wilcoxon signed-rank, one-sided, 10 paired events: p = 0.042

**But agreement was the wrong question on its own, and nearly produced the wrong
answer.** Two models can agree perfectly and both be useless; what the project needs
is the better ANALYST. Scored separately on each model's own proposals — free, since
`test_novel_condition` is local compute:

                    proposals   testable   median p   p<0.10
    Sonnet                 52         19      0.531        3
    Haiku                  13          6      0.640        0

Haiku proposes on 10 of 34 events where Sonnet proposes on 26 — **a quarter of the
hypotheses at a third of the price.** Per unit of what the project actually needs
the two cost the same: **\$0.025 per testable candidate for Sonnet, \$0.026 for
Haiku**, and Sonnet delivers three times the material in the same wall-clock time,
with three proposals under p=0.10 against none.

The nominal saving is \$11.12 per replay (\$16.68 → \$5.56) and it is illusory.
**Cost per call is a meaningless metric when two models do not do the same amount of
work** — the comparison had to be per testable candidate, and only the quality
measurement makes that visible.

**A finding worth more than the model choice.** Sonnet's self-agreement is a median
of 0.388: asked the same question twice it proposes conditions firing on well under
half the same days. The proposal step is largely non-deterministic, and a single
replay samples one grammar out of many that the same system would have produced.

**The test also caught a live defect before it reached a replay.** On the first run,
**35% of Sonnet calls (14 of 40) returned a thinking block with no text at all** and
had to be discarded. Cause: `max_tokens` was 2000 while the mean output on the
current prompt is 1,438 — the cap sat barely above the average, and the prompt had
grown (a three-phase episode narrative, a clause cap, two proposals, the
`within_days` explanation). Raised to 4000; the re-run had **0 failures in 102
calls.** Haiku, averaging 276 output tokens, never hit either cap. No unit test could
have found this: it only appears when the system runs.

**A related correctness fix that's also a cost fix:** every Sonnet call in this project sets `max_tokens=4000`, after live testing showed the model spending an unpredictable, sometimes-large share of its output budget on an unrequested "thinking" block. It was 2000 until 2026-09-01, when the Haiku comparison measured that **35% of Sonnet calls (14 of 40) were returning a thinking block with no text at all**: mean output on the current prompt is 1,438 tokens, so the cap sat barely above the average, and the prompt had grown (a three-phase episode narrative, a clause cap, two proposals). The re-run had 0 failures in 102 calls. Raising it costs nothing unless the model uses the room — `max_tokens` is a ceiling, not a request, the same distinction that once made a cost forecast here 4x too high. Haiku, averaging 276 output tokens, never hit either cap.

### 🚀 Part 2 — Running Live, Ongoing Cost (Anthropic API Only — Excludes Any Dedicated Server/Hosting)

This is the recurring monthly cost once the system is actually deployed and left running — **API usage only**. Keeping the hourly/weekly jobs alive 24/7 needs a host of some kind (a small VPS, a scheduled cloud job, etc.); that cost is separate and not estimated here.

Production's own escalation call (`sonnet_compression_response()`) was measured directly against real production state and comes to **~1,400 tokens/call** (~$0.01/call) — smaller than the Q&A path ever was before Part 1's fix, since it was never affected by that growth in the first place (it never calls `build_live_test_summary()`, only the small, bounded `build_context_summary()`). This figure will drift up slowly as production accumulates real dynamic candidates over months (the "already tested" name list in `build_context_summary()` is deliberately uncapped, see Part 1), but stays name-only, not full-detail, so the growth is slow.

Hourly compression scan (Sonnet called only on a confirmed compression exit, and only ONCE per episode — the ledger in `compression_detector.py` is what makes that true; the shock path it replaced tested the volatility STATE, so a multi-day shock re-escalated the same market every hour) + a handful of escalations/day + occasional weekly keep/drop or milestone advice ≈ **$5-10/month** (lower since the hourly Haiku headline screen was removed on 2026-09-02) in moderate activity, likely under $20/month even in an unusually volatile month — a small fraction of Part 1's own replay cost, which compresses years of events into a short, continuous burst and is not representative of live, one-event-at-a-time operation.

### 🖥️ Part 3 — Server / Hosting Cost Optimization (What Stays Off the Live Host)

The live host only needs to run the cheap, real-time-sensitive jobs continuously: the hourly mechanical trigger scan (`execution/live_testing.py::run_once()`, pure pandas/statistics, no LLM), the hourly compression scan (API calls only, no local compute), and the always-on Telegram bot loop (`telegram/bot.py::run_bot()`, idle almost all the time). None of these need meaningful CPU or memory — a minimal VPS handles all of them comfortably.

**One genuinely heavy periodic job is deliberately kept off the live host: `execution/hyperopt_runner.py`.** It was built local-only from the start (see its own module docstring), for reasons that hold up under measurement, not just intent:
- **It's the one real compute cost in this project.** A single candidate at 50 epochs of Freqtrade's Bayesian hyperopt took several real minutes in this project's own testing — compare to the entire weekly candidate battery re-run (`run_all()` / `run_replay_battery()`), which is genuinely cheap: **4.4 seconds measured, for 38 tracked candidates.** Running hyperopt on a growing candidate registry (the historical replay alone reached 96) on a paid, always-on host would be paying 24/7 pricing for a workload that's actually bursty and occasional.
- **It never needs to be fresh.** `classify_status()` never reads its output — it's a second, independent opinion shown alongside the project's own walk-forward numbers, purely informational (see "Freqtrade hyperopt cross-check" in `docs/case_study/methodology-decisions.md`). TP/SL multipliers optimized a month ago are still perfectly usable; nothing downstream blocks on this being current.
- **Its output is one small file.** `execution/hyperopt_results.json` is the only thing that needs to reach the live host — run the cross-check locally (`python3 -m execution.hyperopt_runner`, from the project root; add candidate labels to run only those, `--epochs`/`--timerange` to override the defaults — weekly, monthly, whenever convenient, no cadence is load-bearing) and copy or push that one file over. No sync infrastructure, no shared database, no server-side Freqtrade install at all.

**What this does *not* apply to:** the weekly candidate battery refresh itself (`scheduler/weekly_revalidation.py`) is real compute, but small enough (seconds, not minutes, even at dozens of candidates) that there's no real hosting-cost incentive to move it off the live host — doing so would only add sync complexity (its output, unlike hyperopt's, actually gates what the live system treats as `accepted`/`watch`/`rejected`) for a cost saving too small to matter.

## Trade Execution (Phase 2, Module B) — `execution/`

This project never opens a funded position (see [methodology-decisions.md](docs/case_study/methodology-decisions.md)) — the files below are grouped by which of the two live models they belong to.

**Live testing (the actual current model — no TP/SL, no funded position):**
- **`live_testing.py`** — Production's real-data counterpart to `replay/engine.py`'s day-by-day walker: `_open_live_test()`/`_check_live_tests()` (hold for the horizon `pattern_significance` found significant, resolve by measuring real forward return/MFE/MAE), `_scan_mechanical_triggers()` (unattended, no LLM, hourly detection, precomputed on the full series before slicing — same lookback-starvation fix as the replay), `find_backdated_entry()` (retroactively anchors a newly-discovered condition's own triggering occurrence to the real hour it first became true, using already-recorded price history — never something a funded order could do, legitimate here since nothing real is ever placed), `check_n50_milestones()` (production's own recurring `MILESTONE_N` confirmation checkpoint, `PRUNE_KEYBOARD_TEMPLATE` buttons, wired from `scheduler/weekly_revalidation.py`) plus `_effective_milestone_count()` (mirrored identically in `replay/engine.py`) — **an occurrence counts when it happened AFTER the hypothesis was written down**, which is the whole rule. That puts two things on the same footing: occurrences accumulated while a proposal sat parked waiting for enough history (in the backtest, not the trade log, but prospective by construction) and live tests opened after registration. It replaced an indiscriminate top-up with the FULL backtest count, under which a condition with 120 historical occurrences reached its checkpoint on day one with no prospective evidence at all — an occurrence from 2019 cannot confirm a hypothesis written in 2023, however uncontaminated the model was. Static candidates are unaffected: they were mined from this history, so none of it postdates them, and the general rule gives them the zero their special case gave (see docs/case_study/methodology-decisions.md). `_check_consecutive_failures()` (fires inside `_check_live_tests()`, immediately after each live test resolves, only for a CONFIRMED candidate — a fast, purely informational early-warning when its last `CONSECUTIVE_FAILURE_ALERT_THRESHOLD=2` (or more) resolved live tests all came back negative, showing the last `max(streak, 5)` occurrences and their mean return/MFE/MAE ratio for context; never changes any candidate's status — see docs/case_study/methodology-decisions.md for why a well-established candidate's own aggregate statistics are, by design, far too slow to react to a real regime change on their own). `run_once()` (entry point for a scheduled job: resolves due live tests, then scans every tracked trigger).
- **`live_test_state.py`** — Persistent state for the above (`live_tests.json`, `horizons.json`) — mirrors `replay/state.py`'s equivalent subset against real, not simulated, data.
- **`hyperopt_runner.py`** / **`freqtrade_bridge.py`** / **`freqtrade_userdir/strategies/hyperopt_candidate_strategy.py`** — A periodic, local-only, purely informational cross-check (see "Cost Optimization" Part 3 above): runs Freqtrade's own (independent) Bayesian hyperopt against this project's real data to re-derive TP/SL multipliers for each tracked candidate. `python3 -m execution.hyperopt_runner` from the project root is a real CLI (`--epochs`/`--timerange`, specific candidate labels, or every tracked candidate by default) — writes `execution/hyperopt_results.json`, the one file that needs to reach a live host. `freqtrade` is imported lazily (inside function bodies) so nothing else in this project gains a hard dependency on it. `_run_one()` never returns a bare failure — every attempt is persisted as `{"status": "ok", ...}` or `{"status": "failed", "reason": ..., "at": ...}`, so a failed or data-starved run is distinguishable from "never attempted."

**Still load-bearing despite the pre-live-testing naming:**
- **`signal_store.py`** — `load_battery_state()`/`BATTERY_STATE_PATH`, imported by `llm_pipeline/context_builder.py`: the pending/active signal split that keeps an approval consumed exactly once and its anchors recoverable days later at exit time. Written for the older Freqtrade path, but it is the live battery-state reader today, not dead code.

The Freqtrade `IStrategy` (`strategies/sentiment_agent_strategy.py`) and its `config_live.json` that used to sit here were **deleted** (commit `d5ce3f6`): under the no-funded-position model nothing loads them, and the TP/SL machinery the hyperopt cross-check actually reuses lives in `freqtrade_userdir/strategies/hyperopt_candidate_strategy.py`.

## Telegram Interface (Phase 4) — `telegram/`

- **`bot.py`** — The long-polling bot process (`run_bot()`). `_send(text, reply_markup=None, pin=False)` — `pin=True` best-effort pins the message (used by `/help`, no special permission needed in this bot's private 1:1 chat); any `text` over Telegram's real 4,096-char limit is split into several messages by `_chunk_message()` (paragraph, then line, then raw-character boundaries, in that preference order, so no HTML tag is ever split mid-message) — a real, previously-silent failure mode: `/replay_summary`'s own "still under test" message once reached 6,880 characters as the dynamic registry grew, and nothing checked `_send()`'s return value at that call site, so the message just never arrived with no error anywhere (see docs/case_study/methodology-decisions.md). Commands (special-cased before the generic dispatch, none touch an LLM): `/summary` (production's `format_trigger_summary()`, fresh, real), `/details <name>` (`candidates/methodology.py::format_candidate_details()` — the full numeric breakdown one candidate's `/summary` line deliberately omits to stay short: the trigger's own exact numeric definition via `_trigger_numeric_description()`, N, p-value, excess return, MFE/MAE ratio, coin/year concentration percentages, reference TP/SL backtest stats, and `explain_non_acceptance()`'s reason if not accepted), `/replay_summary`/`/replay_details`/`/replay_status` (same three for the replay), `/help`/`/start` (pinned reference: every command, plus the local-only hyperopt CLI's own reference text), `"replay continue"` (advances the replay). `_trigger_numeric_description(candidate)` mirrors `_trigger_description()`'s static/dynamic lookup but returns `candidates/definitions.py::TRIGGER_NUMERIC_DEFINITIONS` (the precise thresholds behind each static trigger, e.g. "funding z-score below -2.0" vs. `TRIGGER_DESCRIPTIONS`'s prose-only "an extreme funding rate") or, for a dynamic condition, the same `condition_desc()` output (which already carries its own numeric threshold) -- but only ever checks PRODUCTION's dynamic registry (`llm_pipeline/dynamic_candidates.py::registered_specs()`). `_replay_trigger_numeric_description(candidate)` is the real fix for a real bug this caused: `/replay_details` on a candidate discovered only in the replay showed "trigger definition not found," since production's registry was never going to have it -- this second function checks `replay/state.py::load_dynamic_candidates()` instead, mirroring `replay/engine.py::_trigger_description()`'s own lookup, and `/replay_details` uses it. Both `/details` and `/replay_details` also now pass `tp_mult`/`sl_mult` to `format_candidate_details()` -- another real gap, fixed the same way: the data was already returned by `run_all()` (as `live_state`, previously discarded) and available via `replay/state.py::load_battery_status()`, just never read at the one command detailed enough to show it. Button callbacks: `handle_propose_callback()`/`handle_replay_propose_callback()` (Test It / Don't Test It, id-addressed for production, single-slot for the replay), `handle_prune_callback()`/`handle_replay_prune_callback()` (Keep Testing / Drop from Batch), `handle_kpi_callback()` (superseded, see below). Free text falls through to `handle_natural_language()` (Sonnet, grounded only in real computed numbers — never invents a price, a percentage, or a live-test detail).

## Scheduling (Phase 3) — `scheduler/`

- **`live_daemon.py`** — The single real entry point for running this project live: `python3 -m scheduler.live_daemon`, one process, no external cron. Owns the Telegram long-poll loop itself (the same `_get_updates()`/`_dispatch_update()` pair `telegram/bot.py::run_bot()` uses standalone) and, between polls, checks elapsed time against a persisted `live_daemon_state.json` (gitignored — real runtime state, not a durable record) to decide whether it's time to run the hourly jobs (`live_testing.run_once`, `run_compression_scan` — the third, `haiku_sonnet_pipeline.run_once`, was the Haiku headline scan, unwired 2026-09-02) or the weekly one (`weekly_revalidation.run_weekly_revalidation`). Each scheduled job runs through `_run_isolated(name, fn, alert_on_failure=True)` — one job crashing sends a Telegram alert and is retried on its next normal cycle, never taking the whole daemon down; `alert_on_failure=False` for weekly re-validation only, since it already sends its own more specific alert internally before re-raising (avoids double-reporting the same failure). The daemon's own `_get_updates()` call is wrapped in try/except too (a gap `telegram/bot.py::run_bot()` alone still has, documented below) — a network blip during polling backs off and retries rather than crashing the process. State persists across restarts, so a restart doesn't immediately re-fire a job that already ran recently.
- **`weekly_revalidation.py`** — Refreshes market/funding data first, then re-runs the full candidate battery, diffs every candidate's status against the previous run, notifies on change, notifies separately on any candidate's `horizon_changed_to` (set by `run_battery.py` whenever a fresh `pattern_significance` run empirically derives a different horizon than last time), calls `check_n50_milestones()` (production's recurring validation checkpoint) and handles the 2-year keep/drop safety net (`explain_non_acceptance()` gives the specific reason shown to the human, not a generic line) and the shutdown flow. Written and tested end-to-end; run automatically once a week by `live_daemon.py`, no external cron job needed — can still be run on demand directly for testing. Any crash past the data refresh sends a Telegram alert before re-raising, so a silent failure is never indistinguishable from an ordinary "nothing changed" week.

## Offline Experiments — `forecast/`

Everything here answers a question about the SYSTEM, offline and free — no
Anthropic calls, no market claims. It exists because several decisions in this
project (is a gate too tight, is the pipeline broken, is a data backfill worth
building) were being argued from intuition when they were directly measurable.
Results are committed alongside the code so the numbers quoted in
`docs/case_study/methodology-decisions.md` are auditable rather than asserted.

- **`positive_control.py`** — The question a null result cannot answer on its own: *when a signal really is there, does this pipeline find it?* Plants synthetic "sentiment" on days that ARE followed by strong returns (deliberate lookahead — the point is a known ground truth), at three strengths, against a pure-noise arm that must stay silent and an arm of 24 real dated crypto-news events. Verdict: planted signals reach `accepted`, noise reaches `rejected` with +0.61% excess. It also caught a real trap on its first run — registering a synthetic indicator in `NEWS_EVENT_INDICATORS` but not `EVENT_INDICATORS` leaves it inside its own control group, so the nested test compares a condition against itself-minus-itself and returns `insufficient_data`, which surfaces as `watch` and is indistinguishable from a genuine inconclusive result.
- **`grammar_sweep.py`** / **`analyse_sweep.py`** — Enumerates the whole grammar Sonnet draws from (672 conditions, every one carrying a mandatory news/macro clause) and runs each through the real `test_novel_condition`. Because Sonnet only *proposes* while `pattern_significance` decides, this bounds what the replay could ever find — and it tests on the full history where the replay sees only data up to its simulated date, so it is a strict UPPER bound. The decision rule is written in the code, before the run, precisely so it cannot be adjusted to fit the numbers afterwards.
- **`control_sweep.py`** / **`analyse_control_sweep.py`** — The same grammar crossed with five sentiment feeds of *known* quality (planted at three strengths, real news dates, pure noise). Produces the gate autopsy that redirected this project's tuning: of 294 known-good conditions, 92% of those with a valid test and adequate data died at the significance threshold; concentration killed 4 and MFE/MAE killed 0.
- **`market_relative.py`** / **`coin_specific_test.py`** — Whether measuring the outcome relative to the equal-weight basket recovers candidates the significance gate kills. The answer is conditional and both halves matter: it made things *worse* for a market-timing signal (subtracting the market removes the effect faster than the noise, since cross-coin correlation is 0.54), and *better* for a genuinely coin-specific one (2/9 → 6/9 accepted). Hence it can never be a global switch — it belongs in the spec, chosen per hypothesis.
- **`sentiment_power.py`** / **`analyse_sentiment_power.py`** — The go/no-go test for the GDELT backfill (`docs/case_study/TODO.md` item 1), which is the largest remaining item in the project. Models sentiment as a *continuous daily score* rather than a rare binary flag, parameterised by `rho`, the correlation between the feed and the realised forward return — so the output is one checkable number: the minimum feed quality at which anything is discoverable. Swept from oracle (0.30) down through realistic news sentiment (~0.04) to a pure-noise floor that must stay empty.
- **`*.json`** — Committed result sets (672 / 490 / 392 conditions). Every sweep writes after each condition and skips completed work on restart, so a run can be interrupted and resumed freely.

## Tests — `tests/`

- **`test_methodology.py`** — Causality safety (entry never fills on the trigger bar itself), anchor/barrier math, Sortino's downside-only penalty, concentration detection, status classification thresholds, and the shock z-score's backward-looking guarantee. Plus a regression test for every defect the 2026-08-29 audit found: a pattern running opposite to its own traded direction is never `accepted`, a missing `excess_return` is rejected rather than silently passed, unassessable concentration holds at `watch`, a no-losses candidate scores `+inf` rather than being rejected as unusable, `concentration_check` measures whichever return column the caller names, and `path_outcome` returns NaN for an incomplete horizon instead of a silently-clamped short hold.
- **`test_status_history.py`** — The keep/drop-decision and shutdown logic, against an isolated temp file (never the real, committed `status_history.json`).
- **`test_novel_condition_tester.py`** — The indicator/operator/direction whitelist rejects anything outside it at construction time; a multi-clause condition's plain-English rendering is never collapsed to one clause and never leaks a raw indicator/operator name.
- **`test_run_battery.py`** — Integration test against the real historical data: one deliberately-broken candidate must not cost the other candidates their already-computed result.
- Runs automatically on every push via `.github/workflows/tests.yml`.

## Partial Failures & Crashes

What happens when something breaks mid-run, and what still doesn't handle it:

- **`candidates/run_battery.py`** — each candidate (static or dynamic) runs in its own try/except. A failure shows up as `status = "error"` in that week's table and in `meta["failed_candidates"]`, and is retried automatically next run — it does not touch that candidate's `status_history.json` entry (no real verdict was reached) and does not cost any other candidate its result.
- **`data_ingestion/market_data/binance_fetcher.py`** — same isolation per coin: one coin's OHLCV or funding fetch failing (`None` in the report, not `0`) doesn't block the other six.
- **`llm_pipeline/haiku_sonnet_pipeline.py::run_compression_scan()`** — each confirmed compression exit is isolated; a malformed model response for one item is logged and skipped, the rest of that run still gets processed.
- **`scheduler/weekly_revalidation.py`** — the one process-level alert: any exception past the (already-lenient) data refresh sends a Telegram message describing the failure before re-raising. Without this, "no message this week" was ambiguous between "nothing changed" (normal) and "the whole run silently died" — indistinguishable to the human either way.
- **`execution/hyperopt_runner.py`** — a failed or data-starved run is persisted as `{"status": "failed", "reason": ...}`, distinguishable from "never attempted" — not silently swallowed.
- **`llm_pipeline/pending_tests.py`** — proposals expire after 48h rather than sitting in the queue indefinitely if a Test It / Don't Test It button is never pressed.
- **`scheduler/live_daemon.py`** — each scheduled job (`_run_isolated`) is isolated the same way as the loops above, and its own `_get_updates()` call is wrapped in try/except too — a network blip backs off and retries rather than crashing the process.
- **`telegram/bot.py::run_bot()`** — its long-poll loop wraps `_get_updates()` in try/except too (10s backoff, then retries), not just the per-update dispatch. Previously a real, documented gap — closed after it actually crashed the process live: a stray extra `getUpdates` call from outside the loop (Telegram allows only one active long-poll per bot token) returned an HTTP 409 Conflict on the next poll, which was unhandled and killed the whole process. See docs/case_study/methodology-decisions.md.
